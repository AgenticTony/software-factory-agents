# Task Contract — what the factory consumes

The factory never reads a project's planning prose to decide what to do. It reads **`.factory/tasks.json`** (the queue) and **`.factory/project.yaml`** (how to build, check, and ship the project). Both live in the target repo. Schemas: [`factory/data/schema/tasks.schema.json`](factory/data/schema/tasks.schema.json), [`factory/data/schema/project.schema.json`](factory/data/schema/project.schema.json) (shipped in the package, F-51). Draft profiles: [`projects/`](projects/).

Companion docs: [DESIGN-LOCAL-FACTORY.md](DESIGN-LOCAL-FACTORY.md) (architecture + decisions), [VALIDATOR-SPEC.md](VALIDATOR-SPEC.md) (how "done" is proven).

---

## 1. Why a JSON contract, not the markdown

- Prose status ("open — gated on copy research", "blocker cleared, 3/7") is written for humans and gets misread by models. One misread → the factory works on a blocked task, or marks an unfinished one done.
- Anthropic's long-running harness keeps its feature list in JSON because models are less inclined to rewrite JSON than markdown.
- **Agents never write `tasks.json`.** Only the orchestrator does, and only through the state transitions in §3. The markdown queue (e.g. JobFinderOS `docs/work-orders/README.md`) keeps its prose rationale; the status table between `<!-- factory:queue:start -->` / `<!-- factory:queue:end -->` markers is regenerated from `tasks.json`.

## 2. The task record

One record per work item (WO, story, or step). Big items are split into **slices** — the unit one agent session actually builds.

| Field | Meaning |
|---|---|
| `id` | Project's own id, verbatim: `WO-25`, `A-web.1`, `W.1`. |
| `title`, `source` | Human title; path (+ heading anchor) of the doc that owns the detail. The agent is given `source`, so the WO stays the spec. |
| `kind` | `build` · `decision` · `research` · `owner_only` · `docs`. **Only `build` and `docs` are executed.** Decision/research/owner-only tasks are surfaced to you, never attempted (JobFinderOS WO-27 is a decision WO; WO-29/30 are research-gated). |
| `priority` | `P1`–`P3`. Ties broken by queue order. |
| `depends_on` | Task ids. Cross-repo deps are written `repo:id` (e.g. `soloadventurer-mobile:9b`) and are always treated as unmet until a human marks them met. |
| `status` | See §3. |
| `risk` | Static flags declared from the doc: `auth`, `payments`, `rls`, `migration`, `safety`, `privacy`, `new_dependency`, `deploy`, `cross_repo`, `external_service`, `factory_control` (changes to how work is chosen or judged: schemas, contracts, validator config). The validator adds dynamic flags from the diff (§ VALIDATOR-SPEC L0). |
| `gates` | `spec_approval` (bool), `merge` (`human`/`auto`), `deploy` (`human`/`auto`). Any risk flag forces `human` on merge. In v0 everything is `human`. |
| `acceptance` | The **validation contract**: list of `{id, text, check}`. `check.type` is `test` (named test that must fail before / pass after), `command`, `holdout` (scenario id), `prod_probe` (post-deploy check), or `manual` (becomes an owner step). Frozen when the spec is approved: `acceptance_hash` = SHA-256 of the canonical JSON. A changed hash after approval sends the task back to `draft` — except a `done` task, which is **flagged for your review** instead: reopening verified work is a human decision, never automatic. |
| `scope` | F-65: `{paths: [glob, ...]}` — the files this task may change. Non-empty for every `build`/`docs` task (approval refuses without it; the run escalates `scope_missing`), optional in the schema so pre-F-65 entries load. Globs on the scope matcher: `*`/`?` never cross `/`, `**` spans directories, case-sensitive on the exact git path; malformed patterns (absolute, `..`, empty, catch-all, `[...]` classes) refuse at load. Inside `contract_hash`, so widening needs re-approval. F-71: approval computes the risk flags the scope reaches (default-branch tracked files plus literal scope paths) and refuses a contract whose `risk` does not declare them; the importer adds missing flags and lists each addition. L0 fails every changed path outside the scope (plus the profile's `paths.generated` and the task's own contract test files). |
| `out_of_scope` | Optional list of things this task must **not** change or add, e.g. adjacent features that look related. It gives the L2 Spec axis something concrete to check scope creep against (VALIDATOR-SPEC L2). You write it at approval, alongside `acceptance`. It isn't part of `acceptance_hash` (F-04 hashes `acceptance` only), so editing it after approval doesn't send the task back to `draft`. |
| `owner_steps` | `[{text, done}]` — things only you can do (JobFinderOS "Owner steps (not buildable by a session)"; SoloAdventurer 👤 items). |
| `slices` | `[{id, text, status, acceptance_ids}]` — ordered build units. One session builds one slice. |
| `budget` | `{size: S|M, max_attempts, max_turns, wall_clock_min}`. L-sized work must be sliced; the factory refuses an unsliced L. Approval refuses a runnable contract below the profile's `budget_floor` (defaults 60 turns / 30 min, F-71) — a starved budget dies before any validation layer runs. |
| `dependencies` | Optional (F-71): `[{ecosystem: "pypi"|"npm", name}]` — the packages this contract adds. Inside `contract_hash`; names normalise (PEP 503 / lowercase). A direct manifest addition not declared here escalates `new_dependency`; a declared package that passes the registry checks (exists, first release ≥ 30 days old, not a near-miss of a shipped top name — checked parent-side, VALIDATOR-SPEC L0) no longer escalates. A specifier that is not a registry range escalates whatever it declares: npm aliases/git/file/link/workspace sources, PEP 508 direct references, and lock pins whose `resolved`/`integrity` point anywhere but the checked registry install code the checks never see. Approval shows the list and refuses `--yes` while it is set. |
| `attempts` | Append-only log: `{run_id, slice_id, started, ended, outcome, pr, rounds, input_tokens, output_tokens, escalation}`. |
| `attempt_resets` | Append-only log of owner-granted budget resets: `{at, evidence, done_by, slice_id, prior_attempts}` (F-31 fix). The budget for a slice counts only attempts at or after the latest reset marker — history is never deleted, and `factory status` measures keep counting every attempt. |
| `links` | `pr`, `branch`, `execution_record` (where the factory appends its record in the WO doc), `merged`/`revalidated` (F-26), `escalation_pr` (F-72: `links.pr` is an escalation DRAFT PR — never validated, never re-validated or reported ready by the sweep, never counted against `repo.concurrency`; only `recover --accept` or your own hand-merge advances the task, and accept clears the marker). |

## 3. Status set and lifecycle

```
draft ──(you approve spec + contract)──▶ ready ◀──(deps met)── blocked
  ▲                                         │
  │ contract changed                        ▼ orchestrator picks it
  │                                    in_progress ──(attempts exhausted / ambiguity / risk hit)──▶ needs_human
  │                                         │
  │                                         ▼ validator L0–L3 PASS, PR open
  │                                     in_review ──(you merge — v0 always)──▶ deploying
  │                                                                              │
  │                                                     L4 live check FAIL ◀─────┤
  │                                                     → revert + needs_human   │ L4 PASS
  │                                                                              ▼
  │                                                           owner steps open? ── yes ──▶ awaiting_owner
  │                                                                              │ no            │ you tick them
  └─────────────────────────────────────────────────────────────────────────────▼──────────────▼
                                                                                done
```

| Status | Set by | Meaning |
|---|---|---|
| `draft` | importer / you | No approved contract yet. Not eligible. |
| `blocked` | orchestrator | Contract approved, a dependency isn't `done`. |
| `ready` | orchestrator | Eligible to run. |
| `in_progress` | orchestrator | A session owns a slice. Only **one** writer task at a time per repo (v0). |
| `in_review` | orchestrator | Validator passed, PR open, waiting on your merge. |
| `deploying` | orchestrator | Merged; waiting for deploy + live verification. On a profile with no deploy target (`deploy.mechanism` none-form and empty `live_checks`) the run passes straight through `deploying` to `done`/`awaiting_owner` on the merge — nothing will ever deploy or go live to verify, so the merge is the evidence. |
| `awaiting_owner` | orchestrator | **Built and live-verified, owner steps open.** Not done. On a no-deploy profile (`deploy.mechanism` none-form and empty `live_checks`) nothing is live-verified — the merge is the evidence, and the close parks the task here with its owner steps open. This is the "blocker cleared ≠ story done" state both projects already use. |
| `needs_human` | orchestrator | Escalated. `attempts[-1].escalation` says why. Never retried automatically. |
| `done` | orchestrator | All slices merged, L4 live check passed, owner steps ticked. **Requires live evidence — CI green is not enough.** On a no-deploy profile (`deploy.mechanism` none-form and empty `live_checks`) no L4 exists — the merged PR is the evidence, and CI green alone still isn't it: a human reviewed and merged that PR. |
| `not_buildable` | importer | `decision`/`research`/`owner_only` kinds. Listed in your daily summary. |

Recovery and continuation edges (same allowed-transition table, kept out of the diagram for readability):

| Edge | Set when |
|---|---|
| `in_progress → ready` | the run aborted with no PR and no outcome (orchestrator crash, killed session). The task re-enters the queue under the same attempt budget. Liveness comes from a **run lease**, an OS lock the session holds for its whole life and the OS releases when the process dies. `reclaim_abandoned` applies this edge only when the lease is free, so a live run is never reclaimed, and a run that died before its first attempt record still is. |
| `in_review → in_progress` | you rejected the PR — it closes on GitHub, the sweep surfaces the close as `pr_closed`, and `factory recover` queues the fix round (the row remains the manual/replay form of that move). |
| `in_review → needs_human` | stale base (F-26): the default branch moved past the open PR's base and re-validation of the PR merged onto the new base failed — the PR was only ever validated on the base it was built on. F-76: a re-validation that fails a COMMAND (an L0/L1 command exits non-zero; a gate timeout included) re-runs once on a fresh clean clone of the same merged SHA before parking — only a second failure parks; a pass on the re-run stamps the pair and names the flaked findings in the progress entry. A merge conflict and unwaived L0 escalations are deterministic and park after one run. F-75: also `ci_failed` — the PR's own CI stayed red through the run's fix rounds and the budget ran out (see §escalations). |
| `deploying → ready` | the previous slice merged and live-verified (on a no-deploy profile: merged — nothing goes live to verify) and more slices remain. Owner-step and `done` evaluation waits until the last slice merges; a task can only be `done`/`awaiting_owner` with every slice merged. |
| `ready → blocked` | a dependency regressed (its task was reopened or demoted). `sync_readiness` reconciles both directions. |
| `needs_human → in_review` | the sweep moved the escalation back: you re-opened the PR, or resolved the conflict on GitHub and merged it — the task then waits in in_review for the F-14 deploy gate exactly like every merged factory PR (a no-deploy profile — `deploy.mechanism` none-form, empty `live_checks` — closes it instead: `in_review → deploying → done`/`awaiting_owner` in the same run, the merge the evidence), and `links.merged` (the merged PR's URL) makes that PR terminal — never gh-polled, counted, or re-validated again; a later PR on the task is not covered (F-26 recovery). F-72 adds a second writer of the same pair with its own gate: `factory recover <task-id> --accept --evidence "…"` on a `new_dependency`/`risk_path_touched` escalation holding an escalation draft PR — the waiver (task, escalation, exact PR head SHA, contract hash, evidence, who, when) is recorded in the owner ledger, L0 re-runs on that exact head with ONLY that class waived, L1 and review continue as a normal round, and on pass the PR is marked ready (`gh pr ready`) and the task moves here; any new commit on the branch voids the waiver (the head is re-read before the ready mark). The generic transition still refuses these tasks: the accept edge is the dedicated `TaskQueue.recover_accept` writer's alone. F-76 narrows the row's own F-26 half: the generic recovery edge `needs_human → in_review` is now the pr_closed RE-OPEN signal only — a `stale_base` task takes this pair exclusively through dedicated writers: `TaskQueue.recover_pr_merged` (the sweep read GitHub reporting the PR merged) or `TaskQueue.recover_revalidated` (`factory recover <task-id> --revalidate`: GitHub reports the PR open and the PR's CURRENT remote head merged onto the current remote default head passed L0+L1 through the sweep's own code path, re-run included; the passing pair is stamped as `links.revalidated`, a session-less, attempt-free move with a `recovered` progress entry — the owner's word plus machine evidence, no y/N). |
| `needs_human → ready` | the fix-round edge: the sweep applies it when you close (reject) a stale_base PR; `factory recover <task-id>` applies it on your word for any parked `stale_base`/`pr_closed` escalation — recover requires the PR closed (an open PR would hold the concurrency slot and the fix round would wait on it forever). A dependency that regressed while the task was parked routes the move to `blocked` instead, exactly as approval would. Only those escalations holding a PR link can take these edges through the sweep — every other `needs_human` task still has no automatic exit; the other owner-gated exits are `credential_added`, which takes the same edge only via `factory recover <task-id> --evidence …` through a dedicated state-layer method (the generic transition refuses credential tasks; interactive y/N, no `--yes`; see §escalations), and `attempts_exhausted`, which takes it only via `factory recover <task-id> --evidence … --reset-attempts` (same state-layer gating; the reset appends an `attempt_resets` marker instead of touching history — see §escalations). |
| `needs_human → draft` | the contract-changed edge — and, F-72, the reject edge: `factory recover <task-id> --reject` on a `new_dependency`/`risk_path_touched` escalation holding an escalation draft PR closes the PR (never merges) and returns the task to draft with its approval markers cleared (`acceptance_hash`/`approved_at`/`approved_by`), so the contract can change and the old ledger approval authorises nothing (the F-63 hash check). The dedicated `TaskQueue.reject_escalation` writer's gate; the generic edge stays reserved for contract changes. |

Escalation reasons (enum): `attempts_exhausted`, `budget_exhausted`, `risk_path_touched`, `new_dependency`, `protected_path_touched`, `contract_ambiguous`, `quota_exhausted`, `live_check_failed`, `cross_repo`, `pr_create_failed`, `orchestrator_error`, `publish_refused`, `review_not_converging`, `sentinel_failed`, `credential_added`, `stale_base`, `pr_closed`, `scope_missing`, `scope_change_needed`, `ci_failed`.

**F-72 — what an escalation keeps, and how you answer it.** A `protected_path_touched` or `sentinel_failed` hit retries before it escalates (the first strike is an L0 FAIL finding for the next fix round; the same key twice in one run escalates, naming the contract or the project rule as the likely problem — see §sentinel_failed above and VALIDATOR-SPEC L0). **R2 amendment (owner decision 2026-11-12, "1 yes, A with guards"):** the guarded classes keep NO work on GitHub — no push, no PR; the reports stay on disk and the attempt note names the stored report path. Every OTHER escalation raised after a session produced commits on the run branch keeps the work: the parent rebuilds the branch as ONE squashed commit on the base whose message carries `[skip ci]`, pushes it through the existing fence (the secret scan covers the branch's WHOLE history) and opens a **draft PR** — title prefixed `[escalation]`, the factory's `factory-escalation` label, the escalation and report paths in the body, `links.escalation_pr` set, the body stating CI is suppressed until `recover --accept`. Before the push, the base's `.github/workflows/*` are parsed: any `pull_request_target` or `workflow_run` trigger (the two `[skip ci]` cannot suppress, both secrets-bearing) or an unparseable workflow refuses the push as `publish_refused` — the scan covers GitHub Actions only (no non-Actions CI profile field exists yet; a residual). The task stays `needs_human`; the sweep never re-validates an escalation PR or reports it ready, and it holds no writer slot. `credential_added` never pushes (the branch's history holds the credential), `quota_exhausted` re-queues, and the pre-session refusals have no work to keep. A refused or failed escalation push records `publish_refused`/`pr_create_failed` with the original escalation in the note. `new_dependency` and `risk_path_touched` escalations holding a draft PR are answerable in one command — `factory recover <task-id> --accept --evidence "…"`: the waiver (task, class, exact PR head SHA, contract hash) is recorded, L0 re-runs on that exact head with only that class waived, L1 and review continue, and on pass the proven tree is RELEASED — one new commit on the same parent with the same tree (asserted) and NO `[skip ci]`, force-pushed with a lease on the accepted SHA (a concurrent push refuses), the released SHA recorded on the waiver (the sweep matches it; any other new commit voids it), the PR marked ready and the task moved `needs_human → in_review`. `--reject` closes the PR and drafts the task (see the `needs_human → draft` row). `factory loop` parks an escalation and carries on with the next task, printing one line per parked task and exiting 1 so a script never reads "parked" as "all done".

The three orchestrator-side reasons (F-10):

- `pr_create_failed`: the validated branch was pushed but `gh pr create` failed. The task is `needs_human` and `links.branch` names the pushed branch. Open the PR by hand from that branch, or delete it and re-queue.
- `orchestrator_error`: the orchestrator itself failed mid-round (a gate crash, a reviewer timeout). The attempt counts against the budget, the task re-queues, and `loop` stops. Look at the attempt's `note` before running again.
- `publish_refused`: the push fence or the PR-body gate refused, which retrying can't change. The task is `needs_human`; the attempt's `note` says which rule fired.

`review_not_converging` (F-23): a review round's FAIL contained only findings already raised in an earlier round — the loop is bouncing the same findings back and forth, and another round cannot fix that. Re-review now scopes to the delta since the last review and carries repeats instead of re-raising them (BUILD-ORDER F-23); reaching this escalation means those mechanisms see no progress. **F-72: an arbiter settles it first.** Where the stop fires, the parent starts one arbiter session per run — a seat of its own (the reviewer's provider and model by default, overridable with `seat_providers.arbiter`) under a fixed parent-side turn cap — handing it the rendered contract, the diff under review and ONLY the repeated findings (id + text; never the implementer's or reviewer's argument, no session output). It rules each finding through a structured ruling tool: `valid` (one more fix round must resolve it), `invalid` (dropped from this attempt's review, recorded with the reason) or `contract` (the contract itself is at fault). All-`invalid` settles the dispute and the round publishes through the normal gates; `valid` grants exactly one more round; a `contract` ruling, a failed arbiter session (unknown id, missing or malformed ruling), or a second stop after a ruling escalates `review_not_converging` with the rulings attached. The arbiter can never pass L0/L1, approve or merge. A human still decides whatever escalates.

`sentinel_failed` (F-25): a project sentinel — a `sentinels.<risk flag>` command in `project.yaml` — ran because the diff touched that flag's `paths.risk` globs, and failed. **F-72: the first strike retries** — the failure becomes an L0 FAIL finding for the next fix round (naming the sentinel and its output tail, with the instruction to revert the change that trips it); only the SAME sentinel failing again in a later round of the run escalates, its note naming the contract or the project rule as the likely problem. A reverted sentinel change leaves no trace in the published history (a run that converted a guarded strike publishes a squashed commit). Once escalated, the task is `needs_human` with the sentinel's output in the L0 report and the attempt record. Read what the sentinel said: either the change really breaks the project's invariant (reject the PR or fix the project), or the sentinel command itself is wrong (fix it in `project.yaml` by PR).

`credential_added` (F-25): the diff adds a credential-shaped string (a key, token or private-key pattern). Nothing is pushed before a passing round, so the credential sits in the run branch's LOCAL history only — but a retry that later passes would push that earlier commit, so the task is `needs_human` on the round that found it, with no implementer retry. Rotate the credential regardless (the model provider saw it; it is compromised even though nothing was pushed). No history rewrite is needed: re-queueing discards the run branch — each run clones the default branch fresh. The shapes are heuristics; a false positive costs exactly this escalation (`needs_human`, no retry), where a human confirms and re-queues — `factory recover <task-id> --evidence "<what you checked>"` (interactive y/N, no `--yes`; routes `blocked` if a dependency is open, attempts not reset; the evidence, who confirmed and when are appended to the task's progress log) — erring protective is the intent.

`attempts_exhausted`: the task spent its whole `budget.max_attempts` without a passing round. Still never retried automatically — but it is no longer a dead end (F-31: three attempts died to a sandbox bug the code could never fix, and the task had no exit short of a contract change). The owner's word is `factory recover <task-id> --evidence "<what you checked>" --reset-attempts` (interactive y/N, no `--yes`; routes `blocked` if a dependency is open): it re-queues the task and grants a fresh budget by appending an `attempt_resets` marker — `{at, evidence, done_by, slice_id, prior_attempts}` — while every attempt record stays (append-only like `attempts`; the budget counts only attempts after the latest marker, and `factory status` measures keep counting them all). Without `--reset-attempts` the command refuses and says why: the budget is spent, so a plain re-queue would park the task straight back. The evidence, who granted it and how many attempts were reset are appended to the task's progress log.

`stale_base` (F-26, hardened F-76): the default branch moved past an open factory PR's base, and re-running L0 and L1 on the PR merged onto the new base failed (or the merge itself conflicts). F-76's re-run: a failure of a COMMAND (setup/lint/typecheck/test/extra exit non-zero — a gate timeout counts) re-runs the whole re-validation once on a fresh clean clone of the same merged SHA (never the first run's clone, venv or temp files — a flake cannot park a good PR and a real failure cannot be run green); only a second failure parks, the note says it failed twice, and the stored report keeps both runs (the deciding run under the top-level `L0`/`L1` keys, the first under `first_run`). A pass on the re-run is a pass: `links.revalidated` is stamped as today and the progress entry names the first run's failing findings ("failed once, passed on re-run") so a flaky test stays visible. A merge conflict and unwaived L0 escalations are deterministic — they never re-run and park after one run. The PR's validation only ever held on the base it was built on, so the task leaves `in_review` for `needs_human` instead of waiting on a merge that would break `main`. The attempt record's `note` says which step failed and names the conflicting files; the stored report (`<run-id>-revalidate.json`) carries the L0/L1 output. The remedies: F-76 adds the one that keeps the work — `factory recover <task-id> --revalidate`, for a PR GitHub still reports open, re-validates the PR's CURRENT remote head (never the queue's stored one) against the current remote default head through the sweep's own code path, re-run included; a pass moves the task `needs_human → in_review` through the dedicated `TaskQueue.recover_revalidated` writer with the passing pair stamped (the command takes the run lease, runs no session, spends no attempt, asks nothing — the passing re-validation is the evidence; a fail keeps the task parked, stores the new report and exits non-zero naming the failing step). The GitHub actions the next run's sweep reads remain: close (reject) the PR and the sweep moves the task `needs_human → ready` (`blocked` if a dependency is open) for a fix round — which re-implements from the current default head on a fresh run branch, so work pushed to the old PR branch is not reused (capture anything worth keeping in the contract or the review findings first); or resolve the conflict on the branch yourself and merge, and the sweep moves the task back `needs_human → in_review`, where it waits in in_review for the F-14 deploy gate like every merged factory PR (`links.merged` names the merged PR and makes it terminal — nothing in F-26 advances a merged task on a deploy-target profile; a no-deploy profile closes it `in_review → deploying → done`/`awaiting_owner` in the same run, the merge the evidence; reconcile skips non-draft tasks by design). The escalation itself never eats an attempt: sweep escalations are session-less records, so the fix round starts with its slot unspent. `factory run` refuses to report a factory PR ready against a default head it hasn't been validated on, and reports each one it has: one `ready: <pr-url> against <default-branch>@<sha12>` line per open PR the sweep found up to date with, or re-validated on, the current remote head (`factory loop` prints the same under each run). Merge a factory PR only after a run has reported it ready against the current head — on a `branch_protection: unavailable` repo nothing server-side refuses a stale merge. The sweep runs on every off-peak run, with or without pickable work; it only re-validates PRs GitHub still reports open — a merged PR is never re-validated, and a passing re-validation or an up-to-date check is cached in `links.revalidated` so an unchanged pair isn't re-paid.

`pr_closed` (F-26): GitHub reports the PR closed without merging — you closed it, or its head branch was deleted. The task leaves `in_review` for `needs_human` so the close is never silent. From there: re-open the PR on GitHub and the next run's sweep moves the task back `needs_human → in_review` (re-validating it against the current base first); re-open and merge it, and the sweep takes the same path back to `in_review` to wait for the F-14 deploy gate (a no-deploy profile closes it from there instead, as above); or say the fix-round word yourself — `factory recover <task-id>` — which queues `needs_human → ready` for a fix round from the current default head. recover requires the PR closed: it checks GitHub and refuses otherwise (an open PR holds the concurrency slot and the queued fix round would wait on it forever; for a stale_base task, closing the PR alone lets the sweep queue the fix round on its own). The command exists because the PR was already closed when the task parked, so GitHub has no signal left to mean "reject it": a stale_base task parks with its PR open (closing it is the rejection), a pr_closed task parked after the close.

`ci_failed` (F-75): **CI is part of done.** After a validated publish opens or updates a PR, the run waits for the project's own checks on the exact pushed SHA (bounded by `ci_wait_min` in `config.yaml`, default 30 minutes, and the run's remaining wall clock — the wait counts against the wall budget, never against session turns; `ci_wait_min: 0` restores the pre-F-75 behaviour of not reading CI in the run at all). Green ends `pr_opened` as today; nothing reported after the window ends `pr_opened` with the note "no CI reported"; still pending (or unresolvable — never guessed green) with "CI pending". A red is first re-run once per head (`gh run rerun <run-id> --failed` for the failed GitHub Actions jobs — a flake is real, and only a red that survives its re-run counts; a failing check no Actions run backs is red at once). A surviving red becomes a CI FIX ROUND on the same branch and the same PR: the round starts from the pushed head in the same clone, counts against `max_attempts`, runs L0, L1 and review like any round, and its push advances the branch as a fast-forward through the same push fence, leased on the previous pushed SHA (a concurrent push or a force-push under the wait refuses), never force — no new PR, `links.pr` unchanged. The round's prompt carries one finding per failing check — its name and the capped tail of its failing log (`gh run view --log-failed`), or the check's output summary when no Actions run backs it — under the untrusted-data heading: CI logs are produced by code a session wrote, so they are scrubbed of the run's secrets and control-escaped before any prompt, note or stored report. When the attempts (or the wall clock) run out with CI still red, the task parks here: the PR is converted to a draft (`gh pr ready --undo`) and kept open, the note names the failing checks and the stored report path, and the capped tails live in the stored report. The exit is the `attempts_exhausted` one: `factory recover <task-id> --evidence "…" --reset-attempts` (a fresh run re-implements from the current default head on a fresh branch — close the drafted PR first, or the concurrency slot waits on it). F-76 extends the round past the run that published the PR: a factory PR in review whose CI settles red AFTER its run (CI here takes 15–25 minutes against a 30-minute wait) is no longer left for the owner — the sweep, having proved the PR current against the default head, runs F-75's flake guard once per head (re-run the failed Actions jobs, wait again; the re-run head persists on `links.ci_rerun_heads` so a later run never re-runs the same head twice), and a still-red PR takes the fix round through F-75's own machinery: the `in_review → in_progress` edge, a clone of the proved PR head, the failing checks as findings under the untrusted heading, L0, L1 and review as usual, a fast-forward leased push updating the SAME PR, then the CI wait again. The round counts against `max_attempts`; a spent budget parks `ci_failed` with the PR drafted, session-less, exactly the in-run exhaustion. The round starts only when the PR's remote head is still the SHA the factory itself pushed (`links.pushed_head`: the validated publish, F-75's leased update, the accept release — or the owner's vouch). A missing record (a pre-F-76 PR, a crash before the record landed) fails closed with the remedy named in the line; a head moved by anyone else (a hand fix, GitHub's Update branch) is reported `not ready: head moved outside the factory` with the exact vouch command printed, and never built on until the owner vouches: `factory recover <task-id> --revalidate --head <sha>` on the in_review task NAMES the head (the full SHA or an unambiguous ≥12-char prefix — with no gates in the vouch, the owner's sight of the head is the only evidence, so the vouch covers exactly the SHA they judged, never what the remote happens to hold); the remote is read twice under the lease and both reads must resolve the named head (a move or a mismatch refuses, writing nothing), and exactly that head is stamped into `links.pushed_head` — no gates run (the fix round that may build on it runs the full gate stack itself) — never inside the peak window, never on an F-72 escalation draft PR, at most once per run, and the PR being fixed is the open PR (a second PR is never opened). The ready rule follows: `factory run` and the sweep report a factory PR `ready` only when every check on its current head is green — every repo, not only `branch_protection: unavailable` ones; a red PR reads `not ready: CI red (<checks>)`, a pending or unresolvable one `not ready: CI pending`. F-72 escalation draft PRs (`[skip ci]`) are never waited on, and a CI fix round never runs on one.

`scope_missing` / `scope_change_needed` (F-65): the declared-file-scope escalations. Every `build`/`docs` contract declares `scope.paths` — the repo-relative globs its diff may touch, approved with the contract (inside `contract_hash`, so widening is a new contract) and enforced by L0 (`out_of_scope` FAIL findings name every changed path outside them; the task's own contract test files and the profile's owner-approved `paths.generated` globs are the only implicit allowances). `scope_missing` parks a task that reached the run without a scope — the fail-closed half for tasks approved before F-65, ledger-approved or not; it spends no attempt budget (no session ran) and idles the queue rather than spinning. `scope_change_needed` parks a task whose implementer either asked for a wider scope (`request_scope(path, reason)` — the request escalates at once, never widens anything itself) or kept the same out-of-scope file after a fix round told it to revert. The exit is yours: widen (or drop) `scope.paths` in the queue, record the re-approval with `factory adopt` (it shows the contract and records the current hash; `factory approve` refuses non-draft tasks), then `factory recover <task-id> --evidence "<what you checked>"` — interactive y/N, attempts not reset; recover refuses while the current contract hash has no ledger entry, so a widened scope you have not re-approved moves nothing.

## 4. Picking the next task

```
eligible = status == ready
           and kind in {build, docs}
           and every depends_on is done
           and no other writer task in_progress for this repo
order by priority, then position in queue
take the first incomplete slice of the first eligible task
```

## 5. The project profile (`.factory/project.yaml`)

The adapter. Everything the factory must know about a repo that isn't in a task.

| Section | Contents |
|---|---|
| `repo` | Local path, default branch, remote, merge method. `branch_protection: unavailable` declares the plan-limit exception (F-26): GitHub answers the protection call with a 403 because the plan can't have protection, and the factory enforces up-to-date itself (re-validating open factory PRs against the current remote default head). `concurrency` caps open factory PRs per repo (default 1; a ready task waits while the limit is taken). |
| `commands` | `setup`, `lint`, `typecheck`, `test`, `build` — exact commands, run from repo root. |
| `baselines` | Path to a baseline file (test counts, known errors) if the project has one. |
| `paths.risk` | Globs whose change adds a risk flag (auth, migrations, RLS, payments, safety). |
| `paths.protected` | Globs workers may not modify: validator-owned tests, contract fixtures, CI config, the factory's own files. Workers may *add* tests elsewhere. The schema-level defaults union in structurally (F-63: `.factory/**`; F-71: the registry-redirecting config files `.npmrc`/`.yarnrc`/`.yarnrc.yml`/`pip.conf`/`pip.ini`/`uv.toml`/`.pypirc` at any depth) — a profile can only widen. |
| `dependency_manifests` | Files whose change means a new/changed dependency (`package.json`, `requirements*.lock`). A `pyproject.toml` modification escalates only when its dependency surface actually changed (VALIDATOR-SPEC L0). |
| `budget_floor` | Optional (F-71): `{max_turns, wall_clock_min}` — the minimum budget a runnable contract may carry; defaults 60/30 when absent or partial. Owner-approved security content (an F-63 group — changing it re-approval-gates the profile) and bounded by F-64's caps; a floor above a cap refuses at load. It bounds the contract, not the per-seat caps. |
| `sentinels` | Per risk flag, a list of `{command, description}` (F-25). Each command runs — after `commands.setup`, only — when the diff touches that flag's `paths.risk` globs; a failure FAILs L0 and escalates `sentinel_failed` (a flag with no `paths.risk` globs is refused at load). The built-in sentinels (credential added, skip marker, assertion removed, lint suppression in risk paths) always run; a credential find also escalates `credential_added` (rotate it: the provider saw it; nothing is pushed yet, and re-queueing starts a fresh branch). |
| `deploy` | Mechanism, whether merge auto-deploys, the deploy command if manual. |
| `live_checks` | Post-deploy commands the orchestrator runs **outside** the sandbox with secrets from the macOS keychain. |
| `holdouts` | Directory outside the repo (`~/factory/holdouts/<project>/`) and how to run it. |
| `docs_allowlist` | Domains the agent may fetch for docs grounding (both projects mandate official-docs lookups). |
| `sandbox.allow_local_binding` | Authorizes srt's `network.allowLocalBinding` for the **gate runner's settings only** (L0/L1 and the stale-base re-validation clone): the project's tests bind sockets. The session seats never receive it — srt's macOS rules also grant outbound connect to every host loopback port, reach model-written session code must not have. Default false. |
| `standards` | Optional repo-relative paths of the project's coding-standards docs (e.g. `CODING_STANDARDS.md`, `CONTRIBUTING.md`). **Read by the L2 reviewer only**, never pushed to the implementer. Mechanical rules belong in L0 tooling, not here. |
| `cross_repo` | Sibling repos whose changes can break this one. v0: any task touching them → `needs_human`. |

**Out-of-scope register (`.factory/out-of-scope/`).** One markdown file per rejected *concept* (not per request): what was rejected, the durable reason, and the requests that asked for it. Only you write it. It's a protected path, and it records rejected enhancements, never features that turned out to exist already. The importer (F-12) and triage (F-18) read it, and a draft that resembles a record is shown to you with the record cited. Matching is by concept, not keyword, and **you confirm the match**: nothing is rejected automatically. Adapted from mattpocock/skills `triage`.

## 6. Onboarding an existing project

1. **Readiness check.** Factory runs `commands.*` on a clean clone. Every command must run unattended and pass (or match the baseline). Fix the repo first if not — a factory on a red repo can't tell its own breakage from existing breakage.
2. **Write `project.yaml`** from the repo's CLAUDE.md / CI config. Drafts for both projects are in [`projects/`](projects/).
3. **Import the queue.** An importer session reads the planning docs and proposes `tasks.json`. **You review the full import diff line by line before it's committed** — bulk-generated state you didn't read is how the wrong-operation-label bug shipped. Every imported task starts in `draft`.
4. **Approve contracts** for the first 2–3 tasks only. The factory starts on those; approve more as it earns trust.
5. **Insert the queue markers** in the markdown so the status table regenerates from `tasks.json`.
