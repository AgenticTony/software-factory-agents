# Validator Spec — how the factory proves "done"

The validator decides whether a slice may become a PR, and whether a task may become `done`. In both your projects the worst defects shipped **with green tests**: SoloAdventurer's SOS, block and report features wrote to tables that didn't exist, and the suites passed because they mock Supabase. JobFinderOS had a migration from an unmerged branch strand production. So the rule is:

> **A claim of "done" needs evidence from the thing users touch — never only from the code that describes it.**

Companion docs: [TASK-CONTRACT.md](TASK-CONTRACT.md) (what a contract is), [DESIGN-LOCAL-FACTORY.md](DESIGN-LOCAL-FACTORY.md) (where the validator sits).

---

## Contract epochs (F-66) — declared rule changes, checked before anything runs

The rules a project loads under (both schema files and the semantic-check functions in `factory/contract.py`) change only through work orders, and every change is DECLARED in [`factory/data/schema/epochs.json`](factory/data/schema/epochs.json): the epoch it raised (a change that tightens — refuses something that loaded before — raises the epoch by one; a refactor, addition or loosening records `tightens: false` and leaves it), the date, the WO, the surfaces, what changed, the violation tags it introduced, and its migration (an owner action with the exact command, or a named automatic rewrite — only `restamp-version`, which re-stamps the queue's top-level `version` on every factory write and touches nothing else, so no approved contract's hash covers it).

Two mechanisms keep the register honest:

- **The CI fingerprint** (`tests/test_f66.py::test_ac_1`): sha256 of each schema file's raw bytes (whitespace included — they ship verbatim) and of every rule-bearing top-level binding of `factory/contract.py` (functions and constants matched by name pattern: `_check*`, `_validate*`, `validate_*`, `load_*`, `scope_*`, `budget_*`, `iter_schema*`, `_provider*`, `_allowlist*`, `apply_profile*`, and the rule constants). The live fingerprint must equal the register's LATEST entry's. A change with no entry fails CI with the instruction to add one. **Coverage bound (residual, stated):** moving a check into a NEW top-level helper matching the pattern is caught (an unlisted rule binding fails); moving it into a helper named outside the pattern (e.g. `_fmt`) is not — the pattern is the fingerprint's declared reach.
- **`factory doctor`**: a read-only pass over every repo the approval ledger records (each profile approval carries `repo_path`) plus `--repo`, collecting ALL violations through all-errors modes of the real loaders, each with its epoch, WO and fix; any finding exits non-zero. `run`/`loop`/`import` run the same checks first and refuse with the full report. Non-fatal findings (a stale-but-valid epoch, draft tasks approval would refuse) are reported, never run-refusing; profile-approval keeps its own enforcement (`require_profile_approval`).

A draft-only stale queue is re-proposed by `factory import` and reviewed as a first import; a task past `draft`, or an unparseable queue, refuses with the tasks named. Nothing ever migrates an approved task's contract.

## The five layers

Each layer catches what the others can't. L0–L3 run before a PR opens; L4 runs after deploy. Any FAIL stops the line for that slice.

| Layer | Runs where | Has secrets? | Catches |
|---|---|---|---|
| **L0 Deterministic gates** | Sandbox (clean clone) | No | Broken build/types/tests; regressions vs baseline; forbidden diffs |
| **L1 Contract proof** | Sandbox | No | Tests that don't actually test the change ("would it fail without it?") |
| **L2 Adversarial review** | Fresh agent session, read-only tools | No | Scope creep, wrong approach, edge cases, mock-only evidence |
| **L3 Holdout scenarios** | Orchestrator, local/preview build | Test creds only | Agent optimising for the visible tests instead of the intent |
| **L4 Live verification** | Orchestrator, after deploy | Yes (keychain) | "Merged ≠ live"; drift between repo and production |

### Before L0 — the contract review (F-80, advisory)

The layers below prove a change against its contract; none of them asks whether the contract is right. `factory review-contract <task-id>` is the one model-judged check that runs BEFORE approval and before any spend on the work: a single read-only `contract_reviewer` session reads the contract and its source document through six fixed lenses (purpose, testability, scope, ambiguity, budget, and F-94's defect_class — other sites of the defect a criterion fixes) and the parent stores its strictly-parsed findings keyed by the contract hash. It is not a layer and not a gate — `factory approve` shows the findings for the current hash and the owner decides; a missing, stale or blocker-carrying review refuses nothing. Its trust rules are the judge seats' own: read-only sandbox plus the workspace-integrity guard, untrusted text fenced as data, the output accepted only as one exact object, every shown value escaped (TASK-CONTRACT §3, "Contract review before approval").

### L0 — Deterministic gates (no model involved)

Run from `project.yaml` on a **fresh clone of the slice's branch**, not the worker's own checkout:

1. `commands.setup`, then `lint`, `typecheck`, `test`, `build`, and every `extra` command. F-73: `commands.setup` also runs in the run clone itself — once per attempt, after the branch is checked out and before the implementer's first session, under the same sandboxed runner and timeout — with the factory's commit identity (`Software Factory <factory@localhost>`) set as repo-local git config first. A setup that exits non-zero, times out, or leaves tracked files modified or untracked files git does not ignore starts no session: the attempt records `setup_failed` (the output tail and the dirty paths in the note), spends no attempt budget, and stops `factory loop` like an orchestrator error. **F-86: a purely mechanical failure gets one repair round, not a new attempt.** When L0 fails and EVERY failing finding is the `lint` or `typecheck` command's own result (`new_error` or `command_failed`, prefixed with the command's name — a diagnostic, not a test failure, sentinel, protected-path, scope or dependency finding, timeout or escalation), the parent runs ONE repair session in the same clone before the attempt is judged failed: the implementer seat at a fixed 10-turn cap (`LINT_REPAIR_TURN_CAP`, shrunk to the implementer budget's remainder — the repair's turns count toward the attempt's implementer turns and `max_turns`, its wall time toward the clock beyond the review reserve), the failing commands' capped output as the only findings under the untrusted-data heading, and an instruction to fix exactly that. No repair runs when the turns, wall clock or peak window cannot fund it (the refusal is traced, naming the cap). L0 then runs again IN FULL on the new head — the same pass, never a weakened one — so the repair's diff passes exactly the gates an implementer round's diff passes, no weaker and no stronger (the sentinels, the diff policy, every command); pass continues to L1 and review as if L0 had passed first time, anything else fails the attempt as today. Residual, named: a suppression or lint/typecheck-config change in a non-risk, in-scope file is not an L0 finding (pre-existing sentinel and dependency-surface scope) — it reaches L2 review in the diff, exactly as an implementer's equivalent edit would. The attempt record's `lint_repair` and one `lint_repair` trace event carry commands, turns and outcome; a repair that dies on quota aborts the attempt like any seat.
2. **Baseline comparison.** Distinguish what the diff broke from what was already red. Reuse SoloAdventurer's `verifier.md` rules verbatim: known errors are exact `file:line` entries from the baseline file, never whole files; test count must not drop without a stated, verified reason.
3. **Diff policy** (computed from `git diff <base>...<branch>`):
   - A file matching `paths.protected` is modified or deleted → FAIL, escalation `protected_path_touched`. The schema-level default control set is `.factory/**` plus the registry-redirecting config files (`.npmrc`, `.yarnrc`, `.yarnrc.yml`, `pip.conf`, `pip.ini`, `uv.toml`, `.pypirc` — root and any depth, F-71 R2-4): they change WHAT every install fetches, so pointing the registry somewhere else is a protected touch on every project, whatever the profile says. This includes the test files named in the approved contract (locked at approval), and — independently of the profile — any tracked path under `.venv/`: the gate runner's venv is factory infrastructure inside the clone, and a committed `.venv` is planted environment (`git add -f`), never project source; the venv creation refuses such a clone before any gate command runs. **F-72: the first strike retries** — the parent converts the escalation into an L0 FAIL finding for the next fix round of the same run (naming the path, or the sentinel and its output tail, with the instruction "revert this; this contract may not change it"); only the SAME key (class + path, class + sentinel name) in a second round of the run escalates, its note naming the contract or the project rule as the likely problem. A strike key's count is never reset by a round that misses it — a different path is a NEW first strike, not a reset of the original's count (A, B, A escalates on the third round). The retry is bounded by the run's existing round and budget limits, and integrity is preserved on the commit history: a run that converted a guarded strike publishes its validated tree as ONE squashed commit on the base, so a reverted protected-path change leaves no trace in any published commit (the push fence's history scan re-proves it for secrets).
   - A changed path outside the task's declared `scope.paths` → FAIL `out_of_scope` (F-65), for every change class — added, modified, deleted, type-change, mode-only, submodule pointer, both sides of a rename, a copy's destination — judged on the exact path string git reports through the scope matcher (`*`/`?` never cross `/`, `**` spans directories, case-sensitive: a case variant or Unicode-normalisation look-alike of an in-scope path is OUT, a symlink is judged by its own path, never its target). Allowed besides the scope: the profile's owner-approved `paths.generated` globs and the task's own contract test files — nothing else is implicit. Scope never overrides protection (both findings fire when both apply), and F-65 gates which FILES change, not what changes inside them: unrelated edits inside an in-scope file stay L2's to catch against `out_of_scope`. A task with no declared scope is not judged here (requiring the scope is approval's and the run's job — `scope_missing`); the same path out of scope in two rounds of one run escalates `scope_change_needed`.
   - A file matching `paths.risk.<flag>` → add the flag to the task; it now needs a human merge, escalation `risk_path_touched` if the flag wasn't declared in the contract.
   - A commit between the merge-base and head whose message carries an AI attribution trailer or footer → FAIL `attribution_trailer` (F-42), on every round before anything is pushed. One pattern list (`factory/attribution.py`), shared with the publish step, covers: a `Co-Authored-By`/`Assisted-by`/`Generated-by` trailer naming an unambiguous AI author (an assistant name or the factory's own seat identity), any trailer line naming a name that is also a human name (Kimi, Gemini, Cursor, …) only when an AI shape sits beside it (a bot/noreply or AI vendor address, or the product's compound name — "Cursor Agent"), any trailer naming an AI vendor address, the bare `AI-assisted:` declaration, and a `Generated with` footer (the phrase followed by an AI tool or vendor link, anywhere in a line — "generated with openapi-generator/faker/ruff" is prose and passes). The publish step refuses the same patterns in a PR's title (unanchored — a title is one line) and its body's FREE TEXT, before the branch is pushed; fenced blocks are skipped, since the implementer's notes and the validator report may legitimately quote a trailer. A squash commit builds its message from that title and the branch's commits, so it cannot inherit a trailer. A human `Co-Authored-By` passes; the branch's own history is rewritten by the implementer in its fix round, never `main`'s.
   - Any `dependency_manifests` file changes → escalation `new_dependency`, **except** what F-71's deterministic parse proves safe: L0 parses what the diff ADDED (base vs head blob at the refs), direct manifests (`requirements*.txt`, `pyproject.toml`'s `[project]` dependency tables, `package.json`'s four dependency maps) and locks (`requirements*.lock`, `package-lock.json` v2/v3 `packages`). "Added" = a name absent at base, or present with a different pinned version; a REMOVED direct dependency still escalates (the contract's `dependencies` declare additions, never removals). Every added DIRECT package must be declared in the task's `dependencies` (normalised names); every added package, direct or transitive, must pass the registry checks — it exists in its registry, its FIRST release is ≥ 30 days old by the parent's UTC clock, and its name is not within Damerau-Levenshtein 1 of a shipped top-package name it is not itself (`factory/data/top_packages/`, regenerated by `scripts/generate_top_packages.py`). The checks run PARENT-side (L0 runs in the orchestrator, outside the sandbox) against the public registry JSON APIs through one injectable, timeout- and size-capped client (`factory.registry`), and their verdicts land on the L0 report as `dependency_checks`. An unreachable registry, a malformed or oversize response (the body cap is measured: 40 MiB, covering npm's largest documents with headroom, streamed so a flood aborts at the cap), a registry answering for another name — fail closed, escalate. The registry calls are sequential and timeout-bounded, so a per-run CAP (30 calls) fails closed on a whole-lock-regen's worth of additions rather than holding L0 for minutes. A specifier that is not a registry range refuses the same way (R1-1): npm aliases (`npm:evil@1`), git/github/file/link/workspace/portal sources, local paths and tarballs in `package.json`; PEP 508 direct references (`name @ …`) in requirements files; `package-lock` `link:` entries, a `resolved` outside `https://registry.npmjs.org/`, and a rotated `resolved`/`integrity` at the same version (the pin is keyed by its full `node_modules` path — nested duplicates are distinct pins). A manifest file ADDED by the diff parses against an empty base side: every entry is judged as an addition (R1-6) — a fully declared new requirements file passes; a deleted one keeps its base side for the removal rule. All pass → no escalation. The pre-F-71 exceptions stand: a plain modification of a root `pyproject.toml` whose dependency surface is unchanged between merge-base and head (the WHOLE parsed document compares, minus the inert allowlist; dependency-bearing tables outside the parsed set — PEP 735 `[dependency-groups]`, `dynamic`, `[tool.uv.sources]`, `[tool.poetry.*]`, an unknown `tool.*` table — escalate), and any manifest with no parser, a parse failure on either side, an added/deleted/renamed pyproject, or a policy call without refs escalates — fail closed. (Hallucinated packages run ~5% for commercial models and ~22% for open ones — the registry checks are the mechanical backstop for the declaration being wrong.) Session-side (F-84): a session's sandbox drops the profile's `network_allowlist` unless the contract declares `dependencies` — installs come from the lock, in the setup that runs before the session (F-73) — and with a declared list the registries are reachable in the session while these parent-side checks judge the manifest.
   - Test files deleted, `skip`/`xfail`/`.only` added, or assertions removed → FAIL.
4. **Sentinels (F-25)** — standing invariants over every diff, each FAILing with the sentinel's name and leaving a result (pass/fail/skipped) on the L0 report, the attempt record and the PR body:
   - Built-ins: a credential-shaped string added (`credential_added` — key, token and private-key patterns; the finding names the shape, never echoes the line, and it ESCALATES: nothing is pushed before a passing round, but a passing retry would push the branch whose local history still holds the credential commit — rotate the credential (the provider saw it) and re-queue; the next run builds a fresh branch. An environment READ — `token = os.environ.get("TOKEN", "")` — is the safe pattern, not a leak: the generic assignment shape is tested with the env call's head and first argument blanked, so the lookup itself is exempt while a 16+ literal anywhere else on the line — a fallback argument, an `or` after the call, a comment's env mention — still flags; the prefix shapes scan env-read lines anyway); a skip, `xfail` or `only` marker added on an existing test (`skip_marker_added` — matched on the line with quoted spans blanked: every statement shape fires — decorators, module-level `pytestmark`, one-line conditionals, `pytest.param` marks — while marker text inside a string fixture stays inert); an assertion removed without a replacement (`assertion_removed` — replacement is per-file arithmetic: verbatim re-adds pair up, a file that ends with as many assertion lines as it started is quiet, only a net loss flags; a replacement must be a real assertion statement — a tautology or a string mentioning "assert" levels nothing); a lint suppression (`# noqa`, `type: ignore`, lint-disable) a risk-path file gains more of than the diff removes (`lint_suppression_added` — net per file and per normalised suppression: the matched comment with whitespace stripped and the rule code(s) kept, so a re-aligned or moved suppression nets to zero while a rule-code swap or a bare `# noqa` replacing a coded one flags; counted only outside string literals, and only where that syntax is a comment in the file's language: `# noqa` inside JSON or markdown prose cannot suppress anything — F-105, after the J-2 run lost an attempt to git re-aligning an unchanged `# noqa: BLE001` as removed plus added); a runner-forgery enabler added in a test file or conftest (`runner_exit_forgery`, F-44 rounds 2-3 — a hard exit/kill, an output-capture escape, a JS runner shape (`process.exit`/`process.kill`/`process.stdout.write`), an outcome-REWRITING hook or assignment (`pytest_runtest_makereport`/`report_teststatus`/`runtest_logreport`/`runtest_protocol` anywhere in test files or conftest — the conftest is the live surface: a makereport hookwrapper flipping `rep.outcome` forges a real pass with no exit and no capture escape — plus `.outcome =`/`.exitstatus =`/`.testsfailed =` assignments), or a session/reporting hook defined in a TEST file (in a conftest those are the registered plugin surface — F-10's probe writes one — and stay quiet, the outcome/exit/capture patterns and the parser's result-line rule carrying the load there): test code runs inside the runner's process; the line scan flags the enablers, self-kill `os.kill(os.getpid(), …)` excepted as the honest crash-simulation shape (the gate fails on the signal exit it produces), and a human decides). The skip-marker, assertion, runner-forgery and lint-suppression findings echo their line through `redact_credentials`, so a credential on that line prints as `[redacted]`.
   - Project sentinels: `sentinels.<risk flag>` commands in `project.yaml` run (through the sandboxed gate runner) only when the diff touches that flag's `paths.risk` globs — and only after `commands.setup` succeeds, because a sentinel may need the environment setup installs (setup failure records them skipped); a failure FAILs and escalates `sentinel_failed`, with the command output redacted through the credential patterns before it reaches any finding, record or PR body. Untouched flags record their sentinels as skipped; a flag with no `paths.risk` globs is refused at profile load.
5. **Project-specific static checks:**
   - JobFinderOS: single Alembic head; `check_dev_lock.py`; the prompt-version pins in `TestTailorPromptCraft`/calibration tests unchanged unless the contract says so.
   - SoloAdventurer: generated-types `tsc` (catches phantom tables *and* columns); `check-schema-refs.py` for `.from()`/`.rpc()`/`.invoke()` targets.

### L1 — Contract proof ("red-first", mechanised)

Both projects already require "a test that would fail without the change". The validator checks it instead of trusting it:

1. Check out the **base commit**, apply **only** the test files from the diff, run the tests named in the contract's `check.type: test` items → **each must FAIL**.
2. Apply the full diff → each must PASS.
3. Every `acceptance` item must map to evidence: a passing test, a command's exit code, or (for `holdout`/`prod_probe`) a scheduled later check. An item with no evidence → FAIL with `contract_ambiguous` if the item can't be checked as written.

A test that passes on the base commit proves nothing, and this is where false greens get through.

**What L1 can't prove.** Red-then-green shows that the test depends on the change. It doesn't show that the test checks behaviour. Two cases pass L1 and still prove nothing:

- **Red for the wrong reason.** The test is red on base only because the symbol it imports doesn't exist yet (collection or import error), so the run never reached an assertion. This is how red-first legitimately looks for a brand-new function, so L1 can't reject it. It does mean the red phase proved only that the name was missing.
- **Tautological or implementation-coupled assertions.** The expected value recomputes what the code computes (`assert add(a, b) == a + b`), or the test asserts on mocked internal collaborators or call counts instead of the result at a public interface. It goes red on base (the code is missing), green on head, and would stay green under a wrong implementation that mirrors the same logic.

L1 therefore records **how** each ref went red (`assertion` vs `collection`) in its report. Judging assertion quality is L2's job (the test-quality checks below), and holdouts (L3) back it up with checks the agent never sees.

### L2 — Adversarial review (the only model-judged layer)

- **Fresh session**, read-only tools (Read, Grep, Glob, Bash for running checks only). Reuse SoloAdventurer's `verifier.md` as the base prompt: *default verdict FAIL; evidence flips it, claims do not.*
- **Input:** the approved contract, the diff, L0/L1 output (including each ref's red reason). **Not** the implementer's narrative. The reviewer judges what was built against what was asked.
- **Two axes, reviewed separately** (adapted from mattpocock/skills `code-review`). A change can pass one and fail the other, so neither is allowed to mask the other:
  - **Spec:** does the diff implement the contract? It reports acceptance items that are missing or partial, behaviour nobody asked for (scope creep, checked against the contract's `out_of_scope`), and items that look implemented but wrongly. Each finding quotes the acceptance item it concerns.
  - **Standards:** does the diff follow the project's documented standards (`project.yaml` `standards`)? A fixed baseline of named code smells (Fowler, *Refactoring* ch. 3: Mysterious Name, Duplicated Code, Feature Envy, Data Clumps, Primitive Obsession, Repeated Switches, Shotgun Surgery, Divergent Change, Speculative Generality, Message Chains, Middle Man, Refused Bequest) always applies. A documented project standard overrides a smell. A smell is always a judgement call, never a hard violation, so it never blocks on its own. Anything L0 tooling already enforces is skipped. A project with no `standards` runs the baseline only, and the report says so.
  - Standards live with the reviewer, not the implementer: the implementer has the most context pressure, and the reviewer receives a diff and has the least.
- **Mandatory checklist** (from your own incident history):
  - Does any new backend call (table, RPC, edge function, column) exist in the **real schema**, or only in a mock? A test that mocks the client is not evidence the backend exists.
  - Does the change touch only the slice's scope?
  - Loading, error, empty and offline states — and does offline UI report *unknown*, not a false "disabled"?
  - New provider/subscription/cache: what invalidates it, who cancels it, what happens on logout?
  - **Test quality** (the part L1 can't prove). Every contract test, and especially any ref L1 reports as red only by `collection`:
    - Does its expected value come from an independent source (a literal, a worked example, the acceptance text), or does it recompute what the code does?
    - Does it assert through the public interface, or on mocked internal collaborators, private methods or call counts? Mocks belong only at system boundaries (external APIs, time, randomness).
- **Model:** a different model from the implementer where possible. With GLM-only, the self-preference bias is real, so L0, L1 and L3 — none judged by the model — carry most of the weight. F-100's registry makes the split a stack choice: `standard` is zai-only (owner decision 2026-11-19), and `standard-plus` — the opt-in a project reaches through `model_stack` re-approval — runs the defect-hunt seat on another provider (`reviewer.hunt`, anthropic `claude-sonnet-5-5`) beside the zai conformance seat; any seat's model is a one-line registry edit measured first with `factory eval --role`.
- Output: JSON `{verdict, findings: [{id, axis, severity, file, line, text}]}`, with `axis` being `spec` or `standards`, stored as the `validator_report`. A finding with severity `blocking` or `major` on either axis means FAIL (F-41: a surviving major weighs exactly as much as a blocking finding, and a declared pass overrides neither). Findings are not re-ranked across axes.
- **Seat lenses (F-94).** The reviewer seats are not identical: seat 1 (every odd seat) reviews with the base prompt above — contract conformance and the standards axis; seat 2 (every even seat) gets the same base plus a defect-hunt lens (every hunk's enclosing function and the input that breaks it; what each removed line enforced and where the new code re-establishes it; the callers of every changed function and the other sites of each defect class the diff touches, reported with `sibling: true`). A one-seat review gets both. Every review site — the round, the final review, the revalidate path, each seat's repair turn and fresh retry, and the seeded eval — uses the same assignment, and `prompt_versions` hashes each seat's own prompt. The search for sibling sites therefore runs from round one, not only in fix rounds. **Every seat knows the sibling rule (F-96):** the line between "this diff's defect, judged normally" and "an older site of the class, `sibling: true`" sits in the BASE reviewer prompt, word for word for every seat — the hunt lens adds the hunt, never a second copy of the rule — and the fix-round paragraph and the FAIL rule both use it: an older site outside the diff is raised with `sibling: true` (no `missed_earlier` owed), a site inside the delta or a break the delta causes anywhere is raised normally, and a finding the orchestrator rules a sibling never fails the round.
- **Sibling sites cannot block (F-94).** A finding is a `sibling` only when BOTH hold: the reviewer flagged it `"sibling": true` (parsed strictly — only the JSON literal `true`; the claim that the defect predates this diff and is another site of the class), AND the parent proved its `file` resolves to a path tracked at the reviewed head that `base...head` does not change (a rename's old and new path both count as changed; a path that cannot be proven outside the diff — `../`, untracked, a case variant, a symlink into the diff, no file — is not). Either alone keeps the rules above: the flag on a changed file lowers no bar, and an UNFLAGGED finding on an untouched file — a break the diff causes at an unchanged caller — blocks by its severity as always. The base prompt draws that line for every reviewer (F-96). Residual, named: a reviewer that wrongly flags a diff-caused break on an untouched file makes it non-blocking. A sibling never fails the round (nor does a seat's declared fail that rests on siblings alone), is never sent to the implementer, is never cut by the nit budget, and keeps its severity in the report. In a fix round a parent-ruled sibling is never dropped as out of delta (F-96: it owes no `missed_earlier` — it rides the follow-up; the marking runs BEFORE the drop, so the exemption reads the parent's two-condition ruling, never the reviewer's claim alone; every other out-of-delta finding keeps F-23's rule exactly). The verifier still votes on it, and a unanimous major sibling survives a drop vote yet still cannot block. At publish it rides the PR body's open-findings section under its own line and F-82's follow-up draft — from the final review's findings or, when only the fix round's delta review reported it, from that stored delta report (F-96) — whose `scope.paths` takes its file only when it is tracked on the base branch and matches no protected or risk glob — otherwise the criterion says the file was left out and why.
- **One verifier per finding (F-96).** After the fan-out merges, every union finding gets its OWN fresh verifier session — the contract, the diff and that one finding only, never another finding's text — so a mistake on one finding cannot spill onto the others. A `blocking` or `major` finding gets two independent verifier sessions and is dropped only when both vote drop with a reason; one keep, one failed session or one invalid vote keeps it, tagged `important` with the failure named on the finding and in the report's `verifier_error` — which names the FAILED sessions only: the other findings' drops still stand beside it. A split serious vote keeps the keep's tag and reason with the dissent recorded on the finding. `minor` and `note` get one session. The unanimous rule stays on top: a serious finding every reviewer reported survives even two drops, recorded `override_refused`. Sessions run in ONE sliding pool capped by the profile's `verification.parallel` (default 6) — a freed slot takes the next session at once; each session runs at the fixed `VERIFIER_TURN_CAP` (F-64), the remaining wall clock is checked before each session starts, and a session it cannot fund is refused: the run escalates `budget_exhausted` and never publishes unverified. A quota-hit verifier session aborts and requeues the task as before. Every verifier site — round review, final review, revalidate and the seeded eval — runs the one shared fan-out (`factory.orchestrator.run_verifier_fanout`), so the prompts and the vote fold cannot drift (F-48 parity, one layer down); a per-session malformed vote keeps its F-85 ONE repair turn, on that session.

### L3 — Holdout scenarios (agents never see them)

- Stored at `holdouts.dir`, **outside the repo**. The agent sandbox denies reads there. The orchestrator runs them against a local build (JobFinderOS) or a Vercel preview (SoloAdventurer).
- Start with 3–5 end-to-end scenarios per project covering what matters most:
  - JobFinderOS: signup → first hunt completes; a generated draft has zero fabrication-guard flags; landing renders in `/sv`.
  - SoloAdventurer: sign in; block a user and see the row in `blocks`; report a message and see the row in `reports`; join the waitlist.
- Scenarios check **outcomes in the real store**, not UI text. They're the direct guard against the phantom-backend class.
- When a holdout catches something, write a regular test for it *as well*. Holdouts stay secret; the regression test doesn't.

### L4 — Live verification (after deploy)

- Runs `live_checks` from `project.yaml`, chosen by `when`: `every_deploy` always; `risk:<flag>` when the task carries that flag.
- **Merged and deployed are separate facts.** JobFinderOS doesn't deploy on merge, so the orchestrator records `merged` and waits for a deploy before L4. SoloAdventurer deploys on merge, so L4 runs right after the Vercel deployment is ready.
- L4 FAIL → the orchestrator opens a revert PR, sets `needs_human` with `live_check_failed`, and stops the queue for that repo until you look.
- **A task reaches `done` only after L4 passes.** This encodes your standing rule: "merged" ≠ "live" — verify every backend claim against prod.

## Rounds and escalation

```
attempt 1: implement → L0 → L1 → L2
  FAIL → findings back to the implementer (same session context, numbered findings only)
attempt 2: fix → L0 → L1 → L2
  FAIL → one more round
attempt 3: fix → L0 → L1 → L2
  FAIL → needs_human (attempts_exhausted). Never retried automatically.
PASS → L3 → PR opened → the PR's own CI awaited (F-75)
  RED (after one flake re-run per head) → a CI fix round on the same branch
  and PR: findings from the failing checks' capped, escaped logs, L0 → L1 →
  L2 as any round, a fast-forward lease push, CI awaited again — until
  green, the window ends (pr_opened + note), or the budget runs out
  (needs_human, ci_failed: the PR drafted and kept).
PASS → you merge → deploy → L4
```

**CI is part of done (F-75).** The layers above prove the change on the factory's host; the project's own CI is the definition of done the owner merges against (the pilot's font-difference PR passed L0–L2 and was unmergeable). So after every validated publish — open or update — the run reads the checks on the EXACT pushed SHA (`gh_ci_state`, the one CI reader; a check about any other SHA never counts) until they settle or the window ends (`ci_wait_min`, default 30, over the run's remaining wall clock; the wait is wall time, never turns; 0 disables it — the pre-F-75 behaviour). An `unresolvable` answer is pending, never green. Pending means checks were still running or unreadable at the window's end — a FAILED read at the window's end is RED after the one re-run, whether or not the re-run was ever observed taking effect (F-83: a re-run that completes between polls is never seen mid-window, and the window's last completed read is the evidence of record); the mid-window observation guard — a stale pre-re-run failure must not settle red before the re-run had its chance — is unchanged, and so is the in-run fix-round trigger (a settled red). A red that survives its one-per-head flake re-run (`gh run rerun --failed`; a check no Actions run backs is red at once) becomes a fix round whose findings are the failing checks themselves — name plus capped `--log-failed` tail (or output summary) — carried under the untrusted-data heading because CI logs are produced by code a session wrote: scrubbed of run secrets and control-escaped before any prompt, note or stored report, capped per check and in total. The fix round never weakens a gate: L0's sentinels catch a fix that only deletes or skips the failing test, the guarded/escalation paths are unchanged, the push goes through the same content fence as a fast-forward leased on the previous pushed SHA (never force), and no new PR is opened. Nothing is reported `ready` on red or unknown CI — on every repo, whatever its branch-protection setting: red reads `not ready: CI red (<checks>)`, pending or unresolvable `not ready: CI pending`. Exhausted, the task parks `ci_failed` with the PR converted to a draft and kept; the exit is the owner's budget reset (`recover --reset-attempts`): with the PR still open it keeps the PR — the task returns to in_review and the sweep's fix round below repairs it in place (F-77); with the PR closed a fresh run re-implements. F-79 makes that the rule for EVERY park that holds a normal open PR, whatever a fix round ended on (attempts or wall clock spent, a non-converging review, a guard hit, an orchestrator error; `scope_change_needed` after its ledger gate, F-78) — and a fix round's work that passed L0 and L1 but did not publish is no longer lost with the clone: the parent keeps it locally as one factory-built commit on the pushed head (`links.wip`, a bundle under the factory root — never pushed, because an unreviewed head must not reach a PR the sweep could report ready), and the next fix round on that PR starts from it when its parent is still the pushed head on the remote, with that round's review findings in its prompt. The kept commit is input to the round, not evidence: L0, L1, review and the push fence run on the whole range as on any round (TASK-CONTRACT §escalations, F-79). F-76 closes the gap the pilot's second run found — a red that settles AFTER its run's wait window (CI takes 15–25 minutes against a 30-minute wait) is no longer left for the owner: the sweep, having proved an in-review PR current against the default head, runs the same flake guard once per head (the re-run head persists on `links.ci_rerun_heads`, so no later run re-runs it), and a still-red PR takes the SAME fix round through F-75's own machinery — the `in_review → in_progress` hop, the proved head's clone, the leased fast-forward update on the same PR, the full gate stack — counted against `max_attempts`, never inside the peak window, at most one per run, only while the remote head is still the SHA the factory itself pushed (`links.pushed_head` — the validated publish, F-75's leased update or the accept release; a missing record fails closed with the remedy in the line; anything else — a foreign push, GitHub's Update branch — reads `not ready: head moved outside the factory` with the exact vouch command printed, and is never built on until the owner vouches with `factory recover <task-id> --revalidate --head <sha>`: the owner NAMES the head (full SHA or an unambiguous ≥12-char prefix), the remote is read twice under the lease and must resolve it both times, and exactly that head is stamped into `links.pushed_head` — the vouch runs no gates, so the named head, the owner's sight, is the whole evidence), never on an F-72 escalation draft PR, and a spent budget parks `ci_failed` with the PR drafted, session-less, exactly the in-run exhaustion. **Nothing publishes under another identity (F-73).** Before every push — the validated publish, open or update, and F-72's escalation snapshot — the parent checks the author and committer of every commit in base..head: any identity that is not the factory's rebuilds the branch as ONE commit on the base through the same squash with its tree assertion, so the pushed tree is exactly the validated one; the run is not failed (the content was validated — only the attribution is corrected), and the attempt record names the foreign identities found, escaped. An all-factory history keeps its round commits: the rebuild never fires without a foreign identity.

Not every round shares a session: an aborted run re-enters the queue, and a PR you reject comes back as a fix round, maybe days later. A **fresh** session carries no context, so the orchestrator keeps a per-task **progress log**, an append-only record of each attempt's report and findings (from Anthropic's long-running-harness `progress.txt` pattern). The log lives outside the clone, and every new session gets a read-only copy. The agent never edits earlier entries. The log also carries **vent** entries (F-27): every `vent(category, text)` call a session's in-process tool collected is flushed in — one entry per call, the moment the session returns — as owner telemetry for `factory status` (F-11) and the F-19 review; vents never render into fresh-session prompts and never touch the attempt record or the budget. Every run is also **traced live** (F-30): one JSONL event log per run at `<factory_root>/trace/<project>/<run-id>.jsonl`, outside every clone and outside the sandbox's write allowlist — phase starts/ends, each tool call as it happens (the session's stdout carries the events out; the trace path itself is not writable from inside), one gate_check per L0 check, L1 red/green proof and L2 finding with the evidence it looked at, per-session spend, and the attempt's terminal marker. Args and result snippets are capped, the seat token and credential-shaped strings (the L0 sentinel patterns) are `[redacted]` before a line is written — at every boundary, so the writer itself also scrubs the seat token from orchestrator-written error text — and a failing trace write is reported once and changes nothing: a run's outcome never depends on its own observability. The pipe out of the sandbox is untrusted: only `tool_call` events cross it, and the writer's stamps (seq, ts, run, task, attempt) merge after the event, so nothing inside a sandbox can forge a terminal marker or re-stamp history. Trace files are owner-only (0600 under a 0700 dir) — they hold capped snippets of everything a run read and wrote, which on PII-bearing projects is personal data — and `reclaim_runs` prunes them after a retention window (14 days). `factory trace <run-id> [--follow]` prints the whole file in order, read-only; `--follow` keeps printing until the run ends (published, failed or aborted) or can no longer write a marker — a killed run, a trace pruned under the reader — and says why it stopped. A session's toolkit (F-22) is part of the same trust story: a project may give its seats vetted skills, plugins and read-only MCP servers (`toolkit:` in project.yaml, admitted items only, per-seat narrowing for the reviewer); they load from a staged read-only copy outside the clone while `setting_sources` stays empty — nothing reaches a session from the owner's personal Claude setup — and every item is licence-gated, content-hashed on load (a tampered vendored file refuses the index), and admitted only by an owner-approved PR carrying the vetting report (`factory toolkit vet` reads a candidate and never admits). Each attempt records what it loaded as `name@content-hash`, so a later failure can be attributed to a toolkit version.

`max_attempts` defaults to 3, matching your existing `loop.md`. Credential hits escalate **immediately**: never retried (a passing retry would push the branch whose local history holds the credential), never pushed. Risk-path, new-dependency and cross-repo hits escalate immediately too — retrying won't make them safe — but F-72 keeps their work: an escalation raised after a session committed rebuilds the branch as one squashed commit whose message carries `[skip ci]`, pushes it through the whole-history secret fence (refusing first if the base's workflows trigger `pull_request_target` or `workflow_run` — the two `[skip ci]` cannot suppress) and opens a **draft PR** (`links.escalation_pr`), so a green-but-escalated change is never lost, no runner sees it, and the owner always has a diff to judge; `new_dependency` and `risk_path_touched` are then answerable in one command (`factory recover --accept --evidence`, waiver keyed to the exact PR head SHA — the accept re-validates that head and RELEASES the same tree as a clean commit without the marker, lease-pushed — or `--reject`). The re-validation fetches the branch from the remote into the work clone's `refs/factory/accept/<branch>` (a remote-only branch works — F-101) and proves the head REACHABLE from that ref before any gate runs: a force-push past the reviewed SHA, or a sha the branch does not reach, refuses with the force-push message; presence in the object store alone never suffices. Protected-path and sentinel hits retry once before escalating (above, and TASK-CONTRACT §escalations) and, once escalated, keep no work on GitHub (the R2 amendment: their content is what no runner should see; the reports stay on disk, the note names the path). A non-converging review goes to one arbiter session per run before the owner (TASK-CONTRACT §review_not_converging). `factory loop` parks an escalation and carries on — the batch never idles behind one task's bad luck — and exits 1 when anything was parked.

Merge order (F-26) guards the same invariant one level up: a PR's validation only holds on the base it was built on, so before `factory run` reports an open factory PR ready, it checks ordering. Admission: a repo whose default branch doesn't require status checks with `strict` (branches up to date) refuses to run at all — except a plan-limited repo (GitHub's 403) that declares `repo.branch_protection: unavailable`, where the factory enforces the equivalent itself. Ordering inside the run: a drained queue inside the peak window returns idle whatever the clock says; the window returns before any gate work or gh lookup; off-peak, every run — with or without pickable work — resolves the GitHub state of each open PR **once** (idle ticks touch only `in_review` links plus the recovery-eligible `needs_human` ones, a set computed once and handed to the sweep; a failed lookup is presumed open, so the open-PR limit fails closed while the run itself never crashes on one rotten link) and first applies the recovery edges from that GitHub truth — a re-opened **or merged** escalated PR returns its task to `in_review` (a merged one waits in in_review for the F-14 deploy gate like every merged factory PR, and `links.merged` stamps that PR terminal by URL — never gh-polled, counted, or re-validated again, while a later PR on the same task is not covered; nothing in F-26 advances a merged task on a deploy-target profile — a no-deploy profile (`deploy.mechanism` none-form, empty `live_checks`) closes it `in_review → deploying → done`/`awaiting_owner` in the same run, the merge the evidence), and a closed `stale_base` PR was the owner's rejection: the task goes straight to `ready` for its fix round — `blocked` when a dependency is open, exactly as approval routes — with no lease-less `in_progress` hop. These edges sit outside the general transition table and are gated to a `stale_base`/`pr_closed` escalation holding a PR link — no other `needs_human` task can exit through them (the exceptions are the `credential_added` re-queue, owner-gated to `factory recover --evidence` with an interactive confirm, written only by the dedicated `TaskQueue.recover_credential` method — the generic transition refuses a credential task — and never by the sweep; and the `attempts_exhausted` budget reset, owner-gated to `factory recover --evidence … --reset-attempts` through `TaskQueue.recover_attempts`, which appends an `attempt_resets` marker — history kept, the budget counts only attempts after the latest marker — and is likewise never written by the sweep) — and their escalations never eat an attempt (session-less records; the fix round starts with its slot unspent). A pr_closed task's PR was already closed at escalation, so its fix-round word is `factory recover <task-id>`, which checks GitHub and writes the same gated edge only when the PR is closed (an open PR would hold the concurrency slot under the queued fix round forever; the check fails closed when gh can't answer). The sweep then re-validates the open PRs: `git ls-remote` (prompt-disabled, timed out) skips any PR whose cached `(branch, base)` pair in `links.revalidated` is unchanged — stamped both when a re-validation passes and when the PR is found up to date — and otherwise L0 and L1 re-run on the PR merged onto the new base (locally proving the merge a strict setting would force). A merged PR is stamped in `links.merged` (its URL) and never re-validated or re-polled; its task waits in `in_review` for the F-14 deploy gate, unless the profile has no deploy target (`deploy.mechanism` none-form, empty `live_checks`), in which case the run closes it through `deploying` to `done`/`awaiting_owner` — nothing will ever deploy or go live to verify. A PR closed without merging escalates `pr_closed` so its task is never silently stranded. A failure — merge conflict (read from the index, locale-independent; the local merge runs under `LC_ALL=C` with its own timeout, whose failure wording names the local pathology, not the network) or gates — escalates `stale_base` and the task leaves `in_review` for `needs_human`; every remote git call is prompt-disabled and timed out, and a timeout is a clean RunError, never a traceback. F-76: a gates failure that failed a COMMAND re-runs the whole re-validation once on a fresh clean clone of the same merged SHA (a fresh clone, venv and settings — the first run's leftover state is invisible to the re-run, and a real failure cannot be run green); only a second failure parks, the note says failed twice and the stored report keeps both runs (`first_run` beside the deciding run's top-level keys); a pass on the re-run stamps the pair and names the flaked findings in the progress entry. Merge conflicts and unwaived L0 escalations never re-run. A parked `stale_base` PR GitHub still reports open has an owner-word exit that keeps the work: `factory recover <task-id> --revalidate` re-validates the PR's CURRENT remote head against the current remote default head through the sweep's own code path (re-run included) and on pass moves the task `needs_human → in_review` through the dedicated `TaskQueue.recover_revalidated` writer, stamping the passing pair — session-less, attempt-free, under the run lease. The generic recovery edge `needs_human → in_review` narrowed with it: it is the pr_closed re-open signal only; a merged stale_base PR moves through the dedicated `TaskQueue.recover_pr_merged` writer, never the generic transition. The loop keeps at most one open factory PR per repo (`repo.concurrency`, default 1; counted by GitHub's word — an escalated task's still-open PR holds its slot, an unknown state holds it too, and the picked task's own PR counts like any other, so a fix round waits until you actually close the rejected PR instead of opening a second one and orphaning it), and a `concurrency_wait` names the open PRs and any link whose state couldn't be resolved, so a stall never looks like a healthy tick. Every open PR the sweep proved current — up to date with, or re-validated on, the remote default head, or cached as either for exactly that head — is reported on the run's result and printed as `ready: <pr-url> against <default-branch>@<sha12>`; an unknown-state or failing PR never is. **F-106:** the stamp lands after the pick, so an idle run that stamped one counts it on its result (`merges_stamped`) and `factory loop` runs one more pass instead of stopping `queue_empty` — that pass's own close-merged and readiness sync read the stamped queue (F-93's one merged test, never the sweep's in-memory view) and pick the dependents the merge unblocked; the extra pass follows only a NEW stamp (stamps are terminal), every other stop reason still stops, so a gh reporting the same merged PR on every call costs exactly one extra pass.

## Validating the validator

A validator nobody has tested is just another claim. Monthly, per project:

1. Branch from `main` and seed 5–10 known bugs: a phantom table name, a removed RLS check, an off-by-one, a deleted `await`, a test that mocks the thing it claims to test.
2. Run the validator on each.
3. Record the **catch rate per layer** in the factory metrics. A layer that catches nothing gets fixed or dropped.

The seed set also carries shapes of misses the factory actually had (F-95), each on its own base — a setup commit off the shared fixture, so no other seed sees it: a **sibling seed** (one site of a defect class fixed, a second site in another file untouched — caught only when L2 *passes* and a surviving finding flagged `sibling` names the untouched site; a blocked round is never a sibling catch), a **caller-break seed** (the diff changes a function's return shape and leaves an unchanged caller in another file broken — caught only on a failing round with a finding on the caller's file), and a **clean diff beside an old site** of the class (a sibling finding there is no false fail). Every catch rule names the verdict it requires. Per seed, the report shows `caught k/N repeats` (a quota-voided repeat leaves N), the pass^k line — the seeds caught on every repeat, the reliability number — the seeds never caught (check the seed or grader before the model), and per seed and repeat the findings a seat reported that the verifier then dropped ("found, then dropped", each entry saying whether that run was still caught by any layer, with a count of the drops that cost a catch).

The eval must not tell the reviewers the answer (F-99): the contract every seed's and clean diff's seats see states the developer's task (`contract_title`), as intent — never the seeded defect, and never a marker the diff and fixture don't themselves carry. The one exemption is the gates' own output over the code: a marker in L0/L1's recorded evidence (Python's "coroutine" in a failing test's output) is the gate's finding, never the eval describing the defect. The eval's own description of a seed is a report label no seat reads, the specs' ids never reach a seat either (the contract id, the branch names and the setup/seed commit messages run on opaque `EVAL-NN` slots — L1's red_reason echoes the branch into the review prompt; sentinel descriptions name no seed class), and the clean diffs' changed text states only behaviour the fixture proves (a docstring claiming a state change the code doesn't perform is a false fail waiting to happen).

This is Meta's mutation-testing approach (ACH) applied to the factory's own gates.

The L0 sentinels carry their own standing eval (F-33), run by CI on every PR: a **benign corpus** of this repo's merged PRs — every built-in sentinel must pass every diff; PRs whose credential-shaped test fixtures are correct hits are excluded with the PR and reason recorded — and a fresh **attack corpus** with at least one flagged diff per built-in. `tests/test_f33.py` is the gate; `factory sentinels replay [--corpus benign|attack] [<patch> ...]` replays by hand, read-only. A sentinel change ships only if it stays silent on the benign corpus and still fires on its attacks.

## What's deliberately not here (v0)

- Mutation testing of every PR: too slow and costly on a coding-plan quota. Monthly seeded bugs instead.
- Computer-use UI testing: L3 Cypress/pytest flows cover the critical paths first.
- Auto-merge: no task auto-merges in v0. It's earned per task category once catch rate and revert rate are measured.
